the doctrine

Three ideas carry the whole system

The failure mode is quiet: you install skills and MCP servers for everything you do — development, marketing, product, experiments — and every session loads all of it. The copy skills you added for launch week sit in the context of every refactor. The experimental skill you're trying this week leaks into every repo. Every MCP server is always connected, whether or not this session could possibly need it. Each addition is individually reasonable; the sum is a polluted context and a model that has to ignore most of what it was handed.

Claude Code has no “profiles” feature to fix this — and doesn't need one. Three documented mechanisms compose into something better: a fully repo-native persona system — a persona being, simply, a hat you put on for a kind of work — where a session carries only what the work at hand actually uses.

i.

Plugins are the persona unit

A plugin bundles skills, agents, hooks and MCP servers — and they toggle as one unit via enabledPlugins. Loose skills (e.g. from npx skills add) work too, controlled per-name via skillOverrides — plugins just make the toggle one key instead of many.

ii.

A persona is a directory

One folder per hat — settings.json for capability, mcp.json for context, persona.md for instructions, .env and color for the rest. The settings file rides in on --settings, which outranks every settings file on disk. Folders nest, so hats come in families.

iii.

A base/ is inherited

Any base/ folder is a layer every persona beneath it wears. Root base/ gives all hats chrome-devtools and your house rules; acme/base/ gives the acme family its shared servers; the leaf adds what only it needs. Launch merges the chain, then hands one file to Claude Code.

the shape

Hats can live in a repo, too

In-repo personas — supported out of the box

Nothing extra to configure: from $PWD, clau walks up the tree until it finds a clau/personas/ or .claude/personas/ directory, and that one wins over your global tree. It's an ancestor walk, not a git lookup — a plain directory of projects can carry a shared set of hats for everything beneath it.

Committed, shared — a hat that belongs to the project, not to you. Anyone who clones the repo (with clau + the marketplace) gets it. Committed mcp.json carries ${VAR} placeholders only, never secrets.

Committed override — the repo customizes a global hat: a local designer/ wins over your dotfiles one only while you're inside that tree.

Gitignored, personal — where machine-local settings live. For repos you don't own, .git/info/exclude ignores files for you alone without touching any tracked file.

The override is the whole folder. A repo designer/ holding only settings.json does not inherit the global designer/'s mcp.json or persona.md — those simply don't load. Copy across whatever the repo copy still needs. (base/ layers are unaffected: they resolve independently, so the shared chain still applies.)
A committed persona is a settings layer someone else may have written — it can carry permissions.allow rules. It can't ambush you (you invoke it explicitly, and clau -h shows what resolves), but glance at it before first launch in a freshly cloned repo. Same hygiene as a committed .mcp.json.

the layers

A base, a group, a hat

Once hats are directories, they can nest — and nesting buys inheritance. A folder named base is never launchable; it's a layer that every persona below it wears. Put your house rules in the root base/, your project family's shared servers in acme/base/, and let the leaf carry only what makes it different. One launch collects every layer on the path and merges them into a single settings file, a single stack of MCP configs, and one concatenated system prompt.

The chain is the path

No configuration decides inheritance — the directory path does. clau acme/prod wears base, then acme/base, then acme/prod. Miss out a base/ at some level and that level simply contributes nothing.

Leaf names are enough. clau prod finds acme/prod on its own while that leaf name is unique; the moment a second prod appears anywhere in the tree, clau refuses and names both candidates rather than guessing.

Groups are pure structure: acme/ holds no files of its own and never appears as something you can launch. It shows up in the picker as a heading.

Wearing several hats at once

Name more than one and the session gets the union of all of them — every layer of every hat, deduplicated, merged in one pass. Useful when a task genuinely spans two contexts: the app's staging hat plus the docs hat, the product hat plus a read-only prod hat.

Bare clau opens a picker over the same tree: type to filter, space to toggle as many hats as you want, enter to launch. With nothing toggled, enter takes the highlighted row — so the common case is still two keystrokes. clau -h prints the plain list instead, and is what you want in scripts or over a pipe.

The statusline shows one coloured badge per hat, so a merged session never looks like a single-hat one.

the trap

A leaf cannot switch a base layer off

enabledPlugins merges by OR, so "dev-skills": false in acme/prod loses to "dev-skills": true in acme/base. That is the right rule for merging two chosen hats — you asked for both, you get both — but it means inheritance only ever adds. Keep base/ layers minimal and switch capability on at the leaf; if one hat in a family must not have a plugin, don't enable it in the family's base.

the trap

Permissions only ever widen

Same shape, opposite consequence: deny is a union, so a base layer's denial always survives the merge — good. But allow unions too, so pulling a permissive hat into a merged session widens the other one for that session. Merge deliberately; keep prod-rw alone.

note

Order inside a layer is fixed

Layers apply root-first, leaf-last: persona.md files concatenate in that order, .env keys are overwritten by the deeper layer, and the first color found walking the chain wins. There's no way to re-order them other than moving a directory.

01

Install capability — you probably already have it

Personas don't require authoring anything: they toggle whatever is already installed. Most people get capability from existing marketplaces (/plugin) or the skills ecosystem (npx skills add). The only thing to note down is each plugin's plugin@marketplace name — that's what persona files reference.

Loose skills load in every persona by default; each persona tames them with skillOverrides. Building your own plugins repo is the advanced path — worth it once you have skills of your own to bundle (“One new hat, end to end” below walks through it).

02

Make a directory per hat

mkdir is the whole ceremony. Inside goes settings.json: which plugins are on, which are off (keys exactly as /plugin lists them), loose skills hidden via skillOverrides, plus persona-scoped permissions or suppressed repo MCP servers. The marketer gets copy skills and explicitly no dev or product skills.

Hats live in ~/.claude/personas/ (dotfiles-managed) — one copy for every repo, because context comes later, in mcp.json. Nest them into families when a project has several; put anything shared in that family's base/.

Every file is optional. A hat that only appends instructions is a directory with one persona.md in it, and it launches fine.

03

Give each hat its MCP context

An mcp.json in any layer: the root base/ one loads for every persona (chrome-devtools lives here), a family's base/ covers that project, and the leaf adds what only it needs.

They are additive — they stack on top of the user-level and repo .mcp.json servers, so your dev sessions keep their usual databases. Suppress a specific inherited server with disabledMcpjsonServers in the persona file, or pass --strict-mcp-config for a hermetic session.

Secrets stay out of git: ${ENV_VAR} placeholders only, resolved at launch (see the vault).

Don't hand-edit the JSON. clau-mcp writes it for you and gets the shape right — including type, which is easy to forget. Omit the hat name and it opens the picker, so one server can be written into several hats at once.

~/.claude/clau-mcp.zsh — source after clau.zshclau-mcp() {
  local cmd="$1"; shift 2>/dev/null

  case "$cmd" in
    add)
      local transport="stdio"
      local -a envs headers pos cmdline
      while (( $# )); do
        case "$1" in
          --transport|-t) transport="$2"; shift 2 ;;
          --env|-e) envs+=("$2"); shift 2 ;;
          --header|-H) headers+=("$2"); shift 2 ;;
          --) shift; cmdline=("$@"); break ;;
          -*) print -u2 "clau-mcp: unknown flag $1"; return 1 ;;
          *) pos+=("$1"); shift ;;
        esac
      done

      local persona="" name=""
      if [[ "$transport" == "stdio" ]]; then
        (( ${#cmdline} )) || { cmdline=("${pos[@]:1}"); pos=("${pos[1]}") }
        case ${#pos} in
          1) name="$pos[1]" ;;
          2) persona="$pos[1]"; name="$pos[2]" ;;
          *) print -u2 "usage: clau-mcp add [persona] <name> [--env K=\${VAR}]… -- <command> [args…]"; return 1 ;;
        esac
        (( ${#cmdline} )) || { print -u2 "clau-mcp: missing command"; return 1 }
        set -- "${cmdline[@]}"
      else
        case ${#pos} in
          2) name="$pos[1]"; set -- "$pos[2]" ;;
          3) persona="$pos[1]"; name="$pos[2]"; set -- "$pos[3]" ;;
          *) print -u2 "usage: clau-mcp add [persona] <name> --transport http <url> [--header K:V]…"; return 1 ;;
        esac
      fi

      local -a targets
      if [[ -n "$persona" ]]; then
        targets=("$persona")
      else
        targets=(${(f)"$(_clau_pick_personas)"})
        (( ${#targets} )) || { print "clau-mcp: nothing selected"; return 1 }
      fi

      local envjson='{}' hdrjson='{}' e
      for e in $envs; do
        envjson=$(print -r -- "$envjson" | jq --arg k "${e%%=*}" --arg v "${e#*=}" '.[$k]=$v') || return 1
        [[ "${e#*=}" == \$\{*\} ]] || print -u2 "clau-mcp: ${e%%=*} holds a literal value — prefer \${${e%%=*}} and clau-secret set ${e%%=*}"
      done
      for e in $headers; do
        hdrjson=$(print -r -- "$hdrjson" | jq --arg k "${e%%:*}" --arg v "${${e#*:}## }" '.[$k]=$v') || return 1
      done

      local srv
      if [[ "$transport" == "stdio" ]]; then
        local bin="$1"; shift
        local argsjson; argsjson=$(printf '%s\n' "$@" | jq -R . | jq -s .)
        srv=$(jq -n --arg c "$bin" --argjson a "$argsjson" --argjson e "$envjson" \
          '{type:"stdio",command:$c,args:$a} + (if ($e|length)>0 then {env:$e} else {} end)') || return 1
      else
        srv=$(jq -n --arg t "$transport" --arg u "$1" --argjson h "$hdrjson" \
          '{type:$t,url:$u} + (if ($h|length)>0 then {headers:$h} else {} end)') || return 1
      fi

      local t dir f tmp
      for t in $targets; do
        dir=$(_clau_persona_dir "$t") || return 1
        f="$dir/mcp.json"
        [[ -f "$f" ]] || print -r -- '{"mcpServers":{}}' > "$f"
        tmp=$(mktemp) || return 1
        jq --arg n "$name" --argjson s "$srv" '.mcpServers[$n]=$s' "$f" > "$tmp" && mv "$tmp" "$f" || { rm -f "$tmp"; return 1 }
        print "added $name → ${f/#$HOME/~}"
      done
      print ""
      jq --arg n "$name" '.mcpServers[$n]' "$f"
      print "\nrestart to pick it up: clau ${targets[1]}"
      ;;

    rm|remove)
      local persona name
      case $# in
        1) name="$1" ;;
        2) persona="$1"; name="$2" ;;
        *) print -u2 "usage: clau-mcp rm [persona] <name>"; return 1 ;;
      esac
      local -a targets
      if [[ -n "$persona" ]]; then
        targets=("$persona")
      else
        targets=(${(f)"$(_clau_pick_personas)"})
        (( ${#targets} )) || { print "clau-mcp: nothing selected"; return 1 }
      fi
      local t dir f tmp
      for t in $targets; do
        dir=$(_clau_persona_dir "$t") || return 1
        f="$dir/mcp.json"
        [[ -f "$f" ]] || { print -u2 "clau-mcp: $t has no mcp.json"; continue }
        tmp=$(mktemp) || return 1
        jq --arg n "$name" 'del(.mcpServers[$n])' "$f" > "$tmp" && mv "$tmp" "$f" || { rm -f "$tmp"; return 1 }
        print "removed $name from ${f/#$HOME/~}"
      done
      ;;

    list|ls)
      local persona="$1" dir f
      if [[ -n "$persona" ]]; then
        dir=$(_clau_persona_dir "$persona") || return 1
        f="$dir/mcp.json"
        [[ -f "$f" ]] && jq -r '.mcpServers | to_entries[] | "  \(.key)  \(.value.type // "stdio")  \(.value.url // .value.command)"' "$f" || print "  (none)"
      else
        for f in "$HOME"/.claude/personas/**/mcp.json(N); do
          print "${${f:h}#$HOME/.claude/personas/}"
          jq -r '.mcpServers | to_entries[] | "  \(.key)  \(.value.type // "stdio")  \(.value.url // .value.command)"' "$f"
        done
      fi
      ;;

    *)
      print "clau-mcp — manage MCP servers inside a persona · omit persona for the picker"
      print "  clau-mcp add [persona] <name> --transport http <url> [--header K:V]…"
      print "  clau-mcp add [persona] <name> [--env K=\${VAR}]… -- <command> [args…]"
      print "  clau-mcp rm  [persona] <name>"
      print "  clau-mcp list [persona]"
      ;;
  esac
}
04

Wire the global launcher

One zsh file in your dotfiles — no per-repo scripts, ever. It defines the picker, the tree scanner, and clau itself. Source it before clau-secret.zsh and clau-mcp.zsh, which reuse its helpers.

clau → the picker over the whole tree: type to filter, space to toggle, enter to launch what's toggled — or the highlighted row if nothing is. It reads the same directories a launch reads, so the list can't drift from reality: it is the reality check. clau -h prints the plain list plus a marketplace cross-check against ~/.claude/plugins/marketplaces/.

clau <hat>… → collects the layer chain for every named hat, merges settings with jq, stacks the mcp.json files, concatenates the persona.md files, resolves ${VAR} placeholders, creates the scratch directory, and execs claude. Unknown or ambiguous names error and name the candidates. Anything after the names passes through: clau designer -c continues the last designer conversation.

The session gets CLAU_PERSONA, CLAU_BADGES and CLAU_SCRATCH — child process only, so your shell stays clean. Want plain claude? Type claude. clau is only for hats.

Needs zsh, jq and rg. The keychain lookups use macOS security; on Linux swap those two calls for secret-tool or pass.
~/.claude/clau.zsh — source it from ~/.zshrc_clau_pick() {
  local -a rows; rows=("$@")
  local -i n=${#rows}
  local -a disp paths sel vis order
  local i j p g
  for (( i = 1; i <= n; i++ )); do
    disp[i]="${rows[i]%%$'\t'*}"
    paths[i]="${rows[i]#*$'\t'}"
    sel[i]=0
  done

  local ofd opened=0
  if { true < /dev/tty } 2>/dev/null; then
    exec {ofd}>/dev/tty; opened=1
  else
    exec {ofd}>&2
  fi

  local cur=1 key c1 c2 ind txt box query="" cancelled=0
  local -a readargs
  if (( opened )); then readargs=(-k 1); else readargs=(-k 1 -u 0); fi
  trap 'print -n "\033[?25h" >&$ofd; return 130' INT
  local -i h=$(( n + 3 ))
  printf '\n%.0s' {1..$h} >&$ofd
  print -n "\e[${h}A\e7\e[?25l" >&$ofd

  while true; do
    order=()
    for (( i = 1; i <= n; i++ )); do
      p="${paths[i]}"; vis[i]=0
      [[ "$p" == '#'* ]] && continue
      if [[ -z "$query" || "${p:l}" == *"${query:l}"* ]]; then vis[i]=1; order+=($i); fi
    done
    for (( i = 1; i <= n; i++ )); do
      p="${paths[i]}"
      [[ "$p" == '#'* ]] || continue
      g="${p#\#}"
      for j in $order; do
        if [[ "${paths[j]}" == "$g" || "${paths[j]}" == "$g/"* ]]; then vis[i]=1; break; fi
      done
    done
    (( cur > ${#order} )) && cur=${#order}
    (( cur < 1 )) && cur=1

    print -n $'\e8\e[J' >&$ofd
    {
      print $'\e[2m  ↑↓ move · space toggle · type to search · ⌃u clear · enter launch · ⌃c cancel\e[0m'
      if [[ -n "$query" ]]; then
        print "  \e[38;5;208m/\e[0m${query}\e[2m — ${#order} match\e[0m"
      else
        print ""
      fi
      for (( i = 1; i <= n; i++ )); do
        (( vis[i] )) || continue
        ind="${disp[i]%%[^ ]*}"
        txt="${disp[i]:${#ind}}"
        if [[ "${paths[i]}" == '#'* ]]; then
          print "    ${ind}\e[1;38;5;244m${txt}\e[0m"
        else
          box="☐"; (( sel[i] )) && box=$'\e[38;5;208m☑\e[0m'
          if (( ${#order} && order[cur] == i )); then
            print "  \e[38;5;208m❯\e[0m ${ind}${box} \e[1m${txt}\e[0m"
          else
            print "    ${ind}${box} ${txt}"
          fi
        fi
      done
      (( ${#order} )) || print $'\e[2m    no match\e[0m'
    } >&$ofd

    read $readargs key || { cancelled=1; break }
    case "$key" in
      $'\n'|$'\r') break ;;
      ' ') (( ${#order} )) && sel[${order[cur]}]=$(( 1 - sel[${order[cur]}] )) ;;
      $'\x7f'|$'\b') query="${query%?}"; cur=1 ;;
      $'\x15') query=""; cur=1 ;;
      $'\x0e') (( cur < ${#order} )) && (( cur++ )) ;;
      $'\x10') (( cur > 1 )) && (( cur-- )) ;;
      $'\e')
        c1=""; c2=""
        if ! read -t 0.05 $readargs c1; then
          if [[ -n "$query" ]]; then query=""; cur=1; else cancelled=1; fi
        elif [[ "$c1" == '[' || "$c1" == 'O' ]]; then
          read -t 0.05 $readargs c2
          case "$c2" in
            A) (( cur > 1 )) && (( cur-- )) ;;
            B) (( cur < ${#order} )) && (( cur++ )) ;;
          esac
        else
          case "$c1" in
            $'\n'|$'\r') break ;;
            ' ') (( ${#order} )) && sel[${order[cur]}]=$(( 1 - sel[${order[cur]}] )) ;;
            [[:print:]]) query+="$c1"; cur=1 ;;
          esac
        fi
        (( cancelled )) && break
        ;;
      [[:print:]]) query+="$key"; cur=1 ;;
    esac
  done
  print -n $'\e8\e[J\e[?25h' >&$ofd
  trap - INT
  (( opened )) && exec {ofd}>&-
  (( cancelled )) && return 1

  local -a out_paths
  for (( i = 1; i <= n; i++ )); do
    [[ "${paths[i]}" == '#'* ]] && continue
    (( sel[i] )) && out_paths+=("${paths[i]}")
  done
  (( ${#out_paths} == 0 && ${#order} )) && out_paths=("${paths[${order[cur]}]}")
  (( ${#out_paths} )) || return 1
  print -l -- $out_paths
}

_clau_persona_dir() {
  local name="$1" pdir="$HOME/.claude/personas" d="$PWD" rdir="" k
  while [[ -n "$d" ]]; do
    [[ -d "$d/clau/personas" ]] && { rdir="$d/clau/personas"; break }
    [[ -d "$d/.claude/personas" ]] && { rdir="$d/.claude/personas"; break }
    d="${d:h}"; [[ "$d" == "/" ]] && break
  done
  [[ -z "$rdir" ]] && rdir="/nonexistent/clau/personas"
  [[ -d "$rdir/$name" ]] && { print -r -- "$rdir/$name"; return 0 }
  [[ -d "$pdir/$name" ]] && { print -r -- "$pdir/$name"; return 0 }

  typeset -A pmap
  local root dd rel
  for root in "$pdir" "$rdir"; do
    [[ -d "$root" ]] || continue
    for dd in "$root"/**/*(/N); do
      rel="${dd#$root/}"
      [[ "${dd:t}" == "base" || "$rel" == */base/* ]] && continue
      [[ -f "$dd/settings.json" || -f "$dd/mcp.json" || -f "$dd/persona.md" ]] && pmap[$rel]="$dd"
    done
  done
  local -a cand
  for k in ${(k)pmap}; do [[ "${k:t}" == "$name" ]] && cand+=("$k"); done
  (( ${#cand} == 1 )) && { print -r -- "${pmap[$cand[1]]}"; return 0 }
  (( ${#cand} > 1 )) && { print -u2 "clau: '$name' is ambiguous — ${(j:, :)cand}"; return 1 }
  print -u2 "clau: unknown persona '$name' — run clau -h to list personas"
  return 1
}

  [[ "$rdir" == "$pdir" || -z "$rdir" ]] && rdir="/nonexistent/clau/personas"

  typeset -A pmap
  local root dd rel
  for root in "$pdir" "$rdir"; do
    [[ -d "$root" ]] || continue
    for dd in "$root"/**/*(/N); do
      rel="${dd#$root/}"

      [[ -f "$dd/settings.json" || -f "$dd/mcp.json" || -f "$dd/persona.md" ]] && pmap[$rel]="$dd"

_clau_rows() {
  typeset -A seenhdr
  local rel dir acc i
  local -a parts
  while IFS=$'\t' read -r rel dir; do
    parts=(${(s:/:)rel}); acc=""
    for (( i = 1; i < ${#parts}; i++ )); do
      [[ -n "$acc" ]] && acc="$acc/$parts[i]" || acc="$parts[i]"
      [[ -n "${seenhdr[$acc]}" ]] && continue
      seenhdr[$acc]=1
      printf '%*s%s\t#%s\n' $(( (i - 1) * 2 )) '' "$parts[i]" "$acc"
    done
    printf '%*s%s\t%s\n' $(( (${#parts} - 1) * 2 )) '' "$parts[-1]" "$rel"
  done < <(_clau_scan)
}

Give the session somewhere to put its mess

Agents generate debris — CSV exports, query results, screenshots, throwaway scripts, notes-to-self. Left to itself the session writes them into your repo, and you spend the session's tail cleaning up git status.

So every launch gets a per-codebase directory outside the repo, created on demand, passed in with --add-dir and exported as $CLAU_SCRATCH. the blast radius

Environments are personas too

Staging and production aren't just different credentials — they're different postures. Model them as one family of hats: shared debug skills in acme/base/, a different mcp.json and permission layer per environment. Which blast radius you're holding is decided at launch, coloured in the statusline all session, and can't drift mid-session.

Same servers, different credentials

Both hats declare the same MCP servers — only the ${VAR} references differ. Files on disk carry shape; values arrive at launch from the shell or the keychain.

the vault

Secrets never touch disk

A hat that talks to production needs a credential, and the file describing that hat is a file you want to commit, sync and read over someone's shoulder. So the files hold placeholders only. ${PROD_DB_URL_RO} is not a secret; it's a name. The value lives in the macOS login keychain as clau:PROD_DB_URL_RO and is handed to one child process at launch.

Resolution, in three rules

At launch clau scans the selected layers' mcp.json for ${NAME} and, for each name: ① already set in your shell → that wins, keychain untouched — which is what makes op run and direnv keep working. ② otherwise read clau:NAME from the keychain. ③ neither → a warning naming the exact fix, the launch continues, and that one server fails.

Everything resolved is exported inside a subshell that wraps claude. Your interactive shell never holds the value, so nothing leaks into the next command, your history, or another session.

.env files in a layer work the same way and cover what isn't an MCP server — a token some skill or Bash command needs. A value of keychain:NAME is resolved identically; anything else is taken literally.

macOS only, because the store is security. On Linux, swap the two security find-generic-password calls in clau.zsh for secret-tool lookup or pass — nothing else changes.

The helper

Never pass a value as an argument — the prompt keeps it out of argv, out of ps, and out of your shell history. Updating is just set again with the same name.

By default the keychain item's ACL is locked, so macOS asks for approval on every read. That's the real gate. Tick “Always Allow” in the dialog, or store with -q, when a secret is low-stakes enough that the prompt is only friction.

These items live in the local login keychain: they never appear in Passwords.app, never sync to another device, and macOS 26 ships no keychain GUI. clau-secret list is the only inventory you have — which is also why the naming convention clau:NAME matters.
~/.claude/clau-secret.zsh — source after clau.zshclau-secret() {
  local cmd="$1"; shift 2>/dev/null
  local silent=0
  [[ "$1" == "-q" ]] && { silent=1; shift }
  local name="$1"

  case "$cmd" in
    set)
      [[ -n "$name" ]] || { print -u2 "usage: clau-secret set [-q] <NAME>"; return 1 }
      local -a acl
      (( silent )) || acl=(-T '')
      print "paste the value for $name, then press enter (input is hidden):"
      security add-generic-password -U -a "$USER" -s "clau:$name" -l "clau:$name" \
        -D "clau secret" -j "used by clau personas via mcp.json lookup" "${acl[@]}" -w || return 1
      if (( silent )); then
        print "stored clau:$name — readable without a prompt"
      else
        print "stored clau:$name — every read asks for your approval"
      fi
      ;;
    get)
      [[ -n "$name" ]] || { print -u2 "usage: clau-secret get <NAME>"; return 1 }
      security find-generic-password -a "$USER" -s "clau:$name" -w
      ;;
    check)
      [[ -n "$name" ]] || { print -u2 "usage: clau-secret check <NAME>"; return 1 }
      if security find-generic-password -a "$USER" -s "clau:$name" >/dev/null 2>&1; then
        print "clau:$name ✓ exists"
      else
        print "clau:$name ✗ missing"; return 1
      fi
      ;;
    list)
      security dump-keychain 2>/dev/null | rg -o '"svce"<blob>="clau:[^"]+"' | sed 's/.*="clau:/clau:/;s/"$//' | sort -u
      ;;
    rm)
      [[ -n "$name" ]] || { print -u2 "usage: clau-secret rm <NAME>"; return 1 }
      security delete-generic-password -a "$USER" -s "clau:$name" >/dev/null 2>&1 && print "removed clau:$name"
      ;;
    *)
      print "clau-secret — keychain store for clau personas"
      print "  clau-secret set [-q] <NAME>   store a value (hidden input · -q = no prompt on read)"
      print "  clau-secret check <NAME>      does it exist"
      print "  clau-secret get <NAME>        print it (prompts unless stored with -q)"
      print "  clau-secret list              list stored names"
      print "  clau-secret rm <NAME>         delete"
      ;;
  esac
}
the trap

The session can read its own environment

A secret injected this way is in the session's environment, so a Bash tool call inside that session can print it. Denying Bash(security*) in your root base/ stops the obvious path and is worth having, but treat it as a speed bump — the keychain approval prompt is the boundary that actually holds.

the trap

Only mcp.json is scanned

The placeholder sweep reads the layers' mcp.json files. A ${VAR} written anywhere else — settings.json, persona.md — is never resolved and never warned about. Put the variable in an .env instead.

note

A warning is not a failure

An unresolved placeholder doesn't abort the launch — the session opens and that one server fails to connect, which reads as “the MCP is broken” much later. clau <hat> --version is the cheap pre-flight: same warnings, no session.

the handoff

Plan in one hat, execute in another

The sharpest use of personas isn't wearing two at once — it's wearing them in sequence, over a single conversation. Explore the codebase, argue the approach and write the plan in a hat that cannot reach production. Then hand the finished thread to a hat that can, without re-briefing it on anything. A conversation is a file on disk; capability is decided at launch. Two independent knobs — and clau is where you turn the second one.

Explore

Read the repo, find the prior art, run the research skills. No prod mcp.json, no write credential — the ability to break something isn't in the process at all.

Shape

same session

Tradeoffs argued in-thread, plan written to thoughts/plans/. The reasoning — and the options you rejected — lives in the conversation, not in the file.

Exit

The thread is now a transcript on disk under ~/.claude/projects/, keyed by directory. Nothing in it records which hat wrote it.

History and capability are separate knobs

Claude Code stores every conversation as a transcript keyed by working directory — ~/.claude/projects/<cwd-slug>/<session-id>.jsonl. It has no concept of a persona, so any hat can pick up any thread ever started in that repo.

clau <persona> decides capability; -c / --resume decides which conversation you land in. Neither constrains the other.

Everything after the persona name passes straight through to claude — the launcher appends your flags last — so the order is always persona first, flags after. That's also how plan mode stacks on top of an already read-only hat.

-c means the most recent conversation in this directory. Run anything else in the repo in between — a quick question, a different persona — and it grabs that one instead. Use --resume when in doubt; -r <term> prefilters the picker.
two knobs# knob one — capability, fixed at launch
$ clau planner --permission-mode plan   # plan mode, on a no-prod hat

# …explore, argue, write thoughts/plans/rate-limit.md, ctrl-d

# knob two — which conversation you land in
$ clau builder -c                # most recent thread in this directory
$ clau builder --resume          # interactive picker
$ clau builder -r "rate limit"   # picker, prefiltered by search term
$ clau builder -r 3f9c8b21-…     # straight to one session id

Fork, don't consume

--fork-session, used with --resume or --continue, writes the continuation under a new session id and leaves the original transcript intact. Without it, the resume consumes the thread: planning and execution become one growing conversation and the clean base is gone.

That turns the plan session into a reusable base. Execution goes sideways? Fork the same clean plan again instead of unwinding a polluted thread. Fork it twice and two hats work from one plan in parallel terminals — builder on the code, prod-ro checking live data — both holding the same reasoning, neither fighting over one transcript.

The low-friction reflex is one line: exit the planning session, type clau builder -c --fork-session. No picker, no id, nothing retyped.

$ clau builder -r 3f9c8b21-… --fork-session   # attempt one
$ clau builder -r 3f9c8b21-… --fork-session   # attempt two, same clean base

# …and the deliberate one, off that same plan:
$ clau prod-rw -r 3f9c8b21-… --fork-session --strict-mcp-config

The transcript carries the thinking. Everything a persona controls is re-read from the new launch line — which is exactly why the relaunch is the boundary, and not a workaround for one.

the trap

Capability changes; context doesn't shrink

The forked thread still holds everything the planning hat read, including any MCP output it pulled. A persona gates what a session can do — never what it already knows. If the next hat must not see something, don't resume: start clean and point it at the plan file.

the trap

It remembers tools it no longer has

A resumed conversation can reach for a skill or MCP server that belonged to the previous hat, and find nothing there. Open the new session with a concrete instruction naming the plan file, so it re-grounds on the artifact instead of on the memory of a tool that's gone.

Everyday moves

The system earns its keep in the loop below: experiments stay quarantined in a sandbox plugin that only the play persona can see, and promotion is a one-line move — not a migration.

a.

Capture

New skill — written by you or pulled with npx skills add — lands in plugins/sandbox-skills/. Never in ~/.claude/skills/, which would leak it everywhere.

b.

Quarantine

"sandbox-skills@my-marketplace": true in play/settings.json — and nowhere else, least of all a base/. Developer, designer and marketer sessions never see it.

c.

d.

Why the persona file wins

Settings merge by precedence. The persona slot sits above every file on disk — only live CLI flags and managed org policy outrank it. What lands in that slot is the already-merged layer chain: clau reduces every settings.json on the path into one temp file and passes that, so Claude Code sees a single settings source, not a stack.

the map

Where capabilities come from

Five sources feed a session. For each one there is exactly one persona-control lever — or none. The doctrine in one sentence: keep the uncontrollable layers nearly empty, and put everything else in plugins.

Project .claude/committed to the repo

Skills in .claude/skills/, MCP servers in repo-root .mcp.json. Loads for every persona by default.

lever Hide skills via skillOverrides; suppress servers via disabledMcpjsonServers — both in the persona file.

User ~/.claude/this machine, all projects

Loose skills (including anything npx skills add -g puts here), user-scope MCP servers, user-enabled plugins. The weakest isolation point — loose skills leak into all personas.

lever (weak) skillOverrides one name at a time. Real fix: migrate loose skills into plugins, keep this layer empty.

Plugins★ the persona unit

Skills + agents + hooks + bundled MCP, from a marketplace. All-or-nothing per plugin.

lever (strong) enabledPlugins in the persona file; /plugin + /reload-plugins mid-session.

Persona mcp.jsonlaunch-time injection

Servers only: one file per layer — the root base/, the family's base/, the leaf — stacked in that order. Additive on top of inherited servers. ${VAR} resolved from shell or keychain at launch.

lever (strong) --mcp-config stacks them; append --strict-mcp-config to make them the only source. clau-mcp edits them.

Bundledships with Claude Code

Built-in skills (/code-review, /init, …) and core tools. Present everywhere.

no lever Not persona-controllable; a same-named skill in any layer above shadows a bundled one.

the fine print

What does not isolate

trap

CLAUDE.md is persona-blind

Repo and user CLAUDE.md load for every persona — keep them neutral. Per-persona instructions have their own home: a persona.md in each layer, concatenated and appended to the system prompt at launch via --append-system-prompt-file.

trap

Loose skills leak

Anything in ~/.claude/skills/ appears in all personas by default. Hide per-persona via skillOverrides — workable — or package into plugins so the toggle is one key.

trap

Sidecars add, they don't replace

Every session still inherits user-level and repo .mcp.json servers on top of the layers' mcp.json. Suppress one via disabledMcpjsonServers in the persona file; for “only mine”, pass --strict-mcp-config through clau.

trap

Inheritance only ever adds

enabledPlugins merges by OR across layers, so a leaf writing "dev-skills": false cannot switch off what its base/ switched on. Enable capability at the leaf and keep base/ layers minimal — see the layers.

trap

A repo hat replaces the whole folder

A repo-local designer/ holding only settings.json shadows the global designer/ entirely — its mcp.json and persona.md stop loading rather than merging in. Copy across whatever the repo copy still needs. base/ layers are resolved separately and are unaffected.

trap

Merging hats widens permissions

permissions.allow is unioned across everything you launch, so pulling a permissive hat into a session relaxes the stricter one for that session. deny unions too — that direction is safe — but never merge prod-ro with anything that can write.

manual

Marketplace add is per-machine

Skip the /plugin marketplace add and every plugin@marketplace key resolves to nothing — the persona silently degrades. clau -h catches this: it cross-checks every key against ~/.claude/plugins/marketplaces/ and flags the missing ones.

manual

Plugin MCP is all-or-nothing

A plugin's bundled servers can't be disabled without the whole plugin. If a persona needs skills-without-servers, split the MCP into its own tiny plugin.

untested

One claim awaits live proof

enabledPlugins via --settings is documented but not yet exercised end-to-end here. Step 06 is the test; fallback is /plugin toggling per session.
