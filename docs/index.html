the doctrine

Three ideas carry the whole system

The failure mode is quiet: you install skills and MCP servers for everything you do — development, marketing, product, experiments — and every session loads all of it. The copy skills you added for launch week sit in the context of every refactor. The experimental skill you're trying this week leaks into every repo. Every MCP server is always connected, whether or not this session could possibly need it. Each addition is individually reasonable; the sum is a polluted context and a model that has to ignore most of what it was handed.

Claude Code has no “profiles” feature to fix this — and doesn't need one. Three documented mechanisms compose into something better: a fully repo-native persona system — a persona being, simply, a hat you put on for a kind of work — where a session carries only what the work at hand actually uses.

i.

Plugins are the persona unit

A plugin bundles skills, agents, hooks and MCP servers — and they toggle as one unit via enabledPlugins. Loose skills (e.g. from npx skills add) work too, controlled per-name via skillOverrides — plugins just make the toggle one key instead of many.

ii.

A persona is a settings file

One JSON per persona — global in ~/.claude/personas/ (dotfiles), or living in a repo's .claude/personas/ when the persona belongs to a project — passed via --settings. It outranks project and user settings, so flipping capability per-persona just works.

iii.

MCP sidecars carry context

Skills say how to work; sidecars say what you're connected to. A shared base gives every persona chrome-devtools; the product persona adds PostHog; the marketer's experimental servers stay in the marketer's file. Zero cross-pollution.

the shape

Hats can live in a repo, too

In-repo personas — supported out of the box

Nothing extra to configure: clau checks the repo first, so a persona file inside a project either shadows your global persona or exists only there. clau -h labels these (repo override). Three patterns fall out:

Committed, shared — a persona that belongs to the project, not to you. Anyone who clones the repo (with clau + the marketplace) gets it. Committed sidecars carry ${VAR} placeholders only, never secrets.

Committed override — the repo customizes a global persona: a local designer.json wins over your dotfiles one only while you're in that repo — extra plugin, tighter permissions, whatever the project needs.

Gitignored, personal — where real credentials may live, machine-local. For repos you don't own, .git/info/exclude ignores files for you alone without touching any tracked file.

A committed persona is a settings layer someone else may have written — it can carry permissions.allow rules. It can't ambush you (you invoke it explicitly, and clau -h shows where it resolves from), but glance at it before first launch in a freshly cloned repo. Same hygiene as a committed .mcp.json.
resolution order — clau <name> (same for .mcp.json and .md sidecars)1. <repo>/.claude/personas/<name>.json   ← repo wins: override or repo-only persona
2. ~/.claude/personas/<name>.json        ← global fallback (dotfiles)

committed project persona — no secrets$ cat emma-repo/.claude/personas/support.json
{ "enabledPlugins": { "copy-skills@my-marketplace": true } }
$ cat emma-repo/.claude/personas/support.mcp.json

gitignored personal persona — credentials allowed# .gitignore — or, in repos you don't own, .git/info/exclude:
.claude/personas/*.local.json
.claude/personas/prod-rw.json

the build

Six steps, all just files

01

Install capability — you probably already have it

Personas don't require authoring anything: they toggle whatever is already installed. Most people get capability from existing marketplaces (/plugin) or the skills ecosystem (npx skills add). The only thing to note down is each plugin's plugin@marketplace name — that's what persona files reference.

Loose skills load in every persona by default; each persona tames them with skillOverrides. Building your own plugins repo is the advanced path — worth it once you have skills of your own to bundle (“One new hat, end to end” below walks through it).

capability comes from wherever you already get it# plugins — from any existing marketplace (one-time add per machine)
> /plugin marketplace add <owner>/<repo>
> /plugin                 # browse & install · note the plugin@marketplace names

# loose skills — from the ecosystem
$ npx skills add someone/design-skills

# your own plugins repo — advanced, only when you outgrow the above
02

Write the persona files

One JSON per persona: which plugins are on, which are off (keys exactly as /plugin lists them), loose skills hidden via skillOverrides, plus persona-scoped permissions or suppressed repo MCP servers. The marketer gets copy skills and explicitly no dev or product skills.

They live in ~/.claude/personas/ (dotfiles-managed) — one copy for every repo, because context comes later, in the sidecars. A repo-local .claude/personas/<persona>.json overrides the global one — a rare escape hatch, not a requirement.

~/.claude/personas/marketer.json{
  "enabledPlugins": {
    "copy-skills@my-marketplace":    true,
    "dev-skills@my-marketplace":     false,
    "product-skills@my-marketplace": false,
    "ui-skills@my-marketplace":      false,
    "sandbox-skills@my-marketplace": false
  },
  "skillOverrides": { "some-loose-skill": "off" },
  "disabledMcpjsonServers": ["postgres-prod-readonly"]
}

// designer.json → ui-skills on · product.json → product-skills on
// developer.json → dev-skills on (launched explicitly: clau developer)
03

Give each hat its MCP context

Two kinds of sidecar, both in ~/.claude/personas/: base (loads for every persona — chrome-devtools lives here) and per-persona (PostHog for product, the marketer's experimental servers for marketer).

Sidecars are additive — they stack on top of the user-level and repo .mcp.json servers, so your dev sessions keep their usual databases. Suppress a specific inherited server with disabledMcpjsonServers in the persona file, or pass --strict-mcp-config for a hermetic session.

Secrets stay out of git: ${ENV_VAR} placeholders in committed sidecars, or gitignore the file entirely.

~/.claude/personas/base.mcp.json      — every persona{
  "mcpServers": {
    "chrome-devtools": {
      "command": "npx",
      "args": ["-y", "chrome-devtools-mcp@latest"]
    }
  }
}

~/.claude/personas/product.mcp.json   — product persona only{
  "mcpServers": {
    "posthog": {
      "command": "npx",
      "args": ["-y", "@posthog/mcp"],
      "env": { "POSTHOG_API_KEY": "${POSTHOG_API_KEY}" }
    }
  }
}

// marketer.mcp.json — whatever they're trying this week;
// blast radius is one file, one persona.
04

Wire the global launcher

One zsh function in your dotfiles — no per-repo scripts, ever. Two behaviors, total:

clau → the self-discovery loop: it scans the same files the launcher reads — persona JSONs (global + this repo), sidecars, the base — and cross-checks every plugin@marketplace key against ~/.claude/plugins/marketplaces/. It never launches anything blind: it shows you the available personas and lets you choose. The list can't drift from reality because it is the reality check.

clau <persona> → settings + sidecars. Unknown name errors and points at the list. If a <persona>.md exists, it's appended to the system prompt (--append-system-prompt-file) — your personal CLAUDE.md for that persona, stacking on top of the shared one, never replacing it. The launch line also hands the persona name to the session as CLAU_PERSONA (child process only), which powers the statusline in the next step. Anything after the name passes through: clau designer -c continues the last designer conversation.

Want plain claude? Type claude. clau is only for hats.

~/.zshrc (dotfiles)# clau            → list available personas
# clau designer   → wear one · flags after the name pass through (clau designer -c)
# plain claude?   → just type claude
clau() {
  local pdir="$HOME/.claude/personas"
  local root; root="$(git rev-parse --show-toplevel 2>/dev/null || pwd)"

  # no persona named → self-discovery: read the same files clau launches from
  if (( $# == 0 )) || [[ "$1" == "-h" || "$1" == "--help" ]]; then
    print "clau — persona launcher · clau <persona> [claude flags…]\n"
    local f name plugins side
    for f in "$pdir"/*.json(N) "$root/.claude/personas"/*.json(N); do
      [[ "$f" == *.mcp.json ]] && continue
      name="${${f:t}%.json}"
      plugins=$(jq -r '[.enabledPlugins // {} | to_entries[] | select(.value) | .key | split("@")[0]] | join(", ")' "$f")
      side=""
      [[ -f "$pdir/$name.mcp.json" ]] && side="global sidecar"
      [[ -f "$root/.claude/personas/$name.mcp.json" ]] && side="repo sidecar"
      [[ "$f" == "$root"/* ]] && name="$name (repo override)"
      printf "  %-24s plugins: %-36s mcp: %s\n" "$name" "${plugins:-none}" "${side:-base only}"
    done
    [[ -f "$pdir/base.mcp.json" ]] && print "\n  base.mcp.json ✓ — loads for every persona"
    # marketplace health: every plugin@marketplace key must resolve on this machine
    local m; local -a pfiles; pfiles=("$pdir"/*.json(N))
    (( ${#pfiles} )) && for m in $(jq -r '.enabledPlugins // {} | keys[] | split("@")[1]' "${pfiles[@]}" | sort -u); do
      if [[ -d "$HOME/.claude/plugins/marketplaces/$m" ]]; then
        print "  marketplace $m ✓"
      else
        print "  marketplace $m ✗ NOT registered → /plugin marketplace add <path>"
      fi
    done
    return
  fi

  # persona launch: settings (repo override → global) + base + persona sidecar
  local persona="$1"; shift
  local -a args mcp; local p
  for p in "$root/.claude/personas/$persona.json" "$pdir/$persona.json"; do
    [[ -f $p ]] && { args+=(--settings "$p"); break; }
  done
  (( ${#args} )) || { print -u2 "clau: unknown persona '$persona' — run clau to list personas"; return 1 }
  [[ -f "$pdir/base.mcp.json" ]] && mcp+=("$pdir/base.mcp.json")
  for p in "$root/.claude/personas/$persona.mcp.json" "$pdir/$persona.mcp.json"; do
    [[ -f $p ]] && { mcp+=("$p"); break; }
  done
  (( ${#mcp} )) && args+=(--mcp-config "${mcp[@]}")
  # persona instructions: your own CLAUDE.md-on-top (repo-local wins)
  for p in "$root/.claude/personas/$persona.md" "$pdir/$persona.md"; do
    [[ -f $p ]] && { args+=(--append-system-prompt-file "$p"); break; }
  done
  CLAU_PERSONA="$persona" command claude "${args[@]}" "$@"
}
05

Show the hat in the statusline

One script, one settings key — and every clau session displays which hat it's wearing. The script reads the session JSON Claude Code pipes to it, plus the CLAU_PERSONA variable the launcher set (the statusline command inherits the session's environment).

Bare claude sessions degrade gracefully: no persona variable, no persona segment — just model and directory.

~/.claude/statusline.sh (dotfiles) — chmod +x#!/bin/sh
input=$(cat)
model=$(printf '%s' "$input" | jq -r '.model.display_name // "Claude"')
dir=$(basename "$(printf '%s' "$input" | jq -r '.workspace.current_dir // .cwd // "?"')")
if [ -n "$CLAU_PERSONA" ]; then
  printf '\033[1;38;5;208m⬢ %s\033[0m · %s · %s' "$CLAU_PERSONA" "$model" "$dir"
else
  printf '%s · %s' "$model" "$dir"
fi

~/.claude/settings.json — add the key{ "statusLine": { "type": "command", "command": "~/.claude/statusline.sh" } }

# result, in a clau designer session:   ⬢ designer · Fable 5 · emma-repo
# result, in a bare claude session:      Fable 5 · emma-repo

the blast radius

Environments are personas too

Staging and production aren't just different credentials — they're different postures. Model them as hats: same debug skills, different sidecars, different permission layers. Which blast radius you're holding is decided at launch, visible in clau -h, and can't drift mid-session.

Same servers, different credentials

Both sidecars declare the same MCP servers — only the ${VAR} references differ. Committed files carry shape; secrets come from the shell.

Three ways to keep credentials out of git, by escalating paranoia: env placeholders resolved by direnv or your keychain · gitignored sidecars (dotfiles manage *.json, exclude the credential-bearing ones) · zero-on-disk via op run.

${VAR} / ${VAR:-default} expansion is documented for .mcp.json; the same parser should cover --mcp-config files — confirm on the first staging flight before trusting it for prod.
~/.claude/personas/debug-staging.mcp.json{ "mcpServers": { "postgres": { …,
    "env": { "DATABASE_URL": "${STAGING_DB_URL}" } } } }

~/.claude/personas/debug-production.mcp.json{ "mcpServers": { "postgres": { …,
    "env": { "DATABASE_URL": "${PROD_DB_URL_RO}" } } } }

# zero secrets on disk — 1Password injects for one process tree:
$ op run --env-file=prod.env -- clau debug-production

Read-only and read-write are different hats

Layered isolation: prod-ro uses an actual read-only database role — the credential itself is the boundary, the persona's deny-list is the second layer. prod-rw holds the write credential but gates every mutating tool behind approval.

Treat prod-rw like sudo: launched hermetically for one specific mutation, closed after. Make prod-ro the reflex; the asymmetry in friction is the feature.

~/.claude/personas/prod-ro.json{
  "enabledPlugins": { "debug-skills@my-marketplace": true },
  "permissions": { "deny": ["Bash(psql*)", "mcp__postgres__execute_sql"] },
  "disabledMcpjsonServers": ["postgres-prod-readonly"]
}

~/.claude/personas/prod-rw.json{
  "enabledPlugins": { "debug-skills@my-marketplace": true },
  "permissions": { "ask": ["mcp__postgres__*", "Bash"] }
}

# the habit:
$ clau prod-ro                          # reflexive
$ clau prod-rw --strict-mcp-config      # deliberate, short-lived
the rhythm

Everyday moves

The system earns its keep in the loop below: experiments stay quarantined in a sandbox plugin that only the play persona can see, and promotion is a one-line move — not a migration.

a.

Capture

New skill — written by you or pulled with npx skills add — lands in plugins/sandbox-skills/. Never in ~/.claude/skills/, which would leak it everywhere.

b.

Quarantine

"sandbox-skills@my-marketplace": true in play.json — and nowhere else. Developer, designer and marketer sessions never see it.

c.

Trial

Use it on real tasks in clau play. Iterate in place: edit the skill, /reload-plugins, retry — no restart.

d.

Verdict

Survivor → git mv into the real plugin. Failure → delete the directory. The sandbox stays lean either way.

…and back to a. for the next experiment — working personas untouched throughout.

One-off skills from the ecosystem

Found “new design skills” on skills.sh or GitHub? Three ways in, by commitment level:

Taste it — npx skills use runs a skill once without installing anything. Perfect for a genuine one-off.

Trial it — install with --copy inside the plugins repo, move the skill folder into the sandbox plugin, and it's quarantined to clau play like any other experiment.

Keep it — promote from sandbox into ui-skills and it ships with the designer persona, in every repo, immediately.

Bare npx skills add drops loose skills into the current project's .claude/skills/ (or with -g, into ~/.claude/skills/) — both are persona-blind. Fine for a five-minute test in one repo; anything that survives moves into a plugin.
the three commitment levels# taste — run once, install nothing
$ npx skills use someone/design-skills@polish-ui

# trial — into the sandbox plugin (quarantined to clau play)
$ cd ~/dev/claude-code-plugins
$ npx skills add someone/design-skills --copy -a claude -y
$ git mv .claude/skills/polish-ui \
         plugins/sandbox-skills/skills/polish-ui

# keep — promote into the designer persona
$ git mv plugins/sandbox-skills/skills/polish-ui \
         plugins/ui-skills/skills/polish-ui

A “researcher” persona with custom skills + custom MCP

The whole flow, condensed to one copy-paste. This is the advanced path from step 01 — your own custom skills, in your own tiny plugins repo that doubles as a personal marketplace. Two files there, two in dotfiles, zero in any project repo.

Why the persona file wins

Settings merge by precedence. The persona slot sits above every file on disk — only live CLI flags and managed org policy outrank it.

LayerRankPersona role
--model, --mcp-config, … CLI flagshighestThe launcher's sidecar flags live here.
Managed org policy·Unused in a solo setup.
--settings file·The persona. Wins enabledPlugins, permissions, hooks, model, env.
.claude/settings.local.json·Machine-local tweaks for all personas in a repo.
.claude/settings.json·Team baseline — the implicit developer default.

the map

Where capabilities come from

Five sources feed a session. For each one there is exactly one persona-control lever — or none. The doctrine in one sentence: keep the uncontrollable layers nearly empty, and put everything else in plugins.

Project .claude/committed to the repo

Skills in .claude/skills/, MCP servers in repo-root .mcp.json. Loads for every persona by default.

lever Hide skills via skillOverrides; suppress servers via disabledMcpjsonServers — both in the persona file.

User ~/.claude/this machine, all projects

Loose skills (including anything npx skills add -g puts here), user-scope MCP servers, user-enabled plugins. The weakest isolation point — loose skills leak into all personas.

lever (weak) skillOverrides one name at a time. Real fix: migrate loose skills into plugins, keep this layer empty.

Plugins★ the persona unit

Skills + agents + hooks + bundled MCP, from a marketplace. All-or-nothing per plugin.

lever (strong) enabledPlugins in the persona file; /plugin + /reload-plugins mid-session.

MCP sidecarslaunch-time injection

Servers only: the shared base (chrome-devtools for every persona) + one persona sidecar (repo-local wins over global). Additive on top of inherited servers.

lever (strong) --mcp-config stacks them; append --strict-mcp-config to make them the only source.

Bundledships with Claude Code

Built-in skills (/code-review, /init, …) and core tools. Present everywhere.

no lever Not persona-controllable; a same-named skill in any layer above shadows a bundled one.

the fine print

What does not isolate

trap

CLAUDE.md is persona-blind

Repo and user CLAUDE.md load for every persona — keep them neutral. Per-persona instructions have their own home: a <persona>.md sidecar, appended to the system prompt at launch via --append-system-prompt-file.

trap

Loose skills leak

Anything in ~/.claude/skills/ appears in all personas by default. Hide per-persona via skillOverrides — workable — or package into plugins so the toggle is one key.

trap

Sidecars add, they don't replace

Every session still inherits user-level and repo .mcp.json servers on top of the sidecars. Suppress one via disabledMcpjsonServers in the persona file; for “only my sidecars”, pass --strict-mcp-config through clau.

manual

Marketplace add is per-machine

Skip the /plugin marketplace add and every plugin@marketplace key resolves to nothing — the persona silently degrades. clau -h catches this: it cross-checks every key against ~/.claude/plugins/marketplaces/ and flags the missing ones.

manual

Plugin MCP is all-or-nothing

A plugin's bundled servers can't be disabled without the whole plugin. If a persona needs skills-without-servers, split the MCP into its own tiny plugin.

untested

One claim awaits live proof

enabledPlugins via --settings is documented but not yet exercised end-to-end here. Step 06 is the test; fallback is /plugin toggling per session.
